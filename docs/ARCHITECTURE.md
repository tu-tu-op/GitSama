# GitSama Architecture

GitSama is a local executable with no server component.

```text
Local Git
   |
Named configured Git hook
   |
GitSama hook handler
   |
Generic GitSama event
   |
Pack resolver
   |
Detached audio process
```

## User-owned state

Configuration, packs, pending branch state, playback coordination, and logs live under the user's GitSama home directory. GITSAMA_HOME can point at a temporary directory for tests. A project working tree receives no files. The only repository-local state used by GitSama is a local Git config override for off-here.

## Git 2.54 and configured hooks

Setup checks the installed Git version before making changes. On a supported Git, it registers one named hook per native event with hook.gitsama-*.event, hook.gitsama-*.command, and hook.gitsama-*.enabled through git config. The command is an absolute, shell-quoted path to the installed executable.

GitSama does not change core.hooksPath, copy files into .git/hooks, remove existing hooks, or wrap Git commands. Git's configured hook runner can therefore execute GitSama alongside traditional and other configured hooks.

## Event handling

Post-commit and post-merge are dispatched after Git succeeds. Pre-push parses Git's local ref stream and classifies unique outgoing commits without fetching. It stops once the threshold is known and falls back to push on errors. Post-checkout ignores file checkouts and clone initialization. Post-rewrite reacts only to the rebase argument.

Reference transactions are processed only in the committed state. Zero object IDs identify branch creation and deletion. A short-lived state record lets branch creation win over the immediate checkout event generated by switch -c and checkout -b.

## Audio, process lifecycle, and failure behavior

By default, GitSama uses a non-blocking detached architecture. However, because modern coding agents (such as Antigravity) and IDE sandboxes manage tool commands in isolated process containers (Windows Job Objects) that kill all child processes upon command completion, GitSama employs an ordered fallback chain:

1. **Tier 1 (Breakaway)**: Spawns a detached worker (`__play`) with `CREATE_BREAKAWAY_FROM_JOB | DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP | CREATE_NO_WINDOW`. If the parent environment allows breakaway, the worker outlives the command seamlessly.
2. **Tier 2 (Outside Container)**: If the Job Object forbids breakaway, GitSama invokes a system-level launcher (WMI `Win32_Process` on Windows, `systemd-run` transient scope on Unix). This creates the worker under a system host (e.g., `wmiprvse.exe`) outside the agent's job container. The successful tier decision is cached under `~/.gitsama/state/launcher_tier.txt`.
3. **Tier 3 (Linger Mode)**: If container escape is unavailable or if explicitly configured (`gitsama mode linger`), GitSama plays the audio directly within the hook process. Playback is strictly bounded by a configurable cap (`linger_cap_secs`, default 2.5s) using `sink.stop()`, ensuring Git commands never hang while guaranteeing that short operations (like commits) complete their audio before the command exits.

### Playback Lock Hardening

Playback uses an atomic directory lock (`~/.gitsama/state/playback.lock/`) to prevent overlapping sounds. To prevent orphaned locks when workers are abruptly killed:
- The owner PID is recorded into `playback.lock/owner_pid` upon acquisition.
- Any subsequent process encountering an existing lock verifies whether the owner PID is still alive via OS process table queries (`OpenProcess` + `GetExitCodeProcess` on Windows, `kill -0` on Unix). If the owner process is dead, the lock is reclaimed immediately without waiting for heartbeat staleness.
- A secondary heartbeat timestamp thread updates `playback.lock/heartbeat` every 250ms for age-based staleness fallback.

### Cold-Start Latency Optimization

To minimize lock contention and time-to-first-sound, workers pre-initialize the audio output device (`rodio::OutputStreamBuilder`) and construct the in-memory audio decoder before acquiring the lock. The sink is paused during pre-fill and started the instant the lock is obtained (zero startup delay during playback).

All hook paths catch failures, write safe diagnostics to `~/.gitsama/logs/gitsama.log`, and return zero. Missing packs, invalid TOML, missing files, state corruption, count failures, and audio device failures cannot block Git.

## Pack security

A pack manifest is data. Every event path must be relative, stay inside the pack root after canonicalization, point to a supported audio extension, and refer to a regular file. Unsafe symlinks and traversal are rejected. No manifest field is executed as a command.
